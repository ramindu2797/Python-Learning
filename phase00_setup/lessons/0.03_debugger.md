# 0.03 — The debugger

The debugger lets you pause code mid-run and look at every variable. It is the single most useful tool for understanding code that someone else — or a coding agent — wrote: you *watch* it run instead of guessing.

## In a notebook

1. Click in the gutter left of a line number to set a **breakpoint** (a red dot). Turn on line numbers with `L` in command mode if you can't see them.
2. Instead of running the cell normally, use the dropdown next to the ▷ button → **Debug Cell**.
3. Execution stops at the breakpoint. The **Run and Debug** side panel shows *Variables*; hovering over a name in the code shows its value.
4. Use the floating toolbar:

| Button | Key | What it does |
|---|---|---|
| Continue | `F5` | run to the next breakpoint |
| Step Over | `F10` | run this line, stop at the next one |
| Step Into | `F11` | go *inside* the function called on this line |
| Step Out | `Shift+F11` | finish this function, stop in the caller |
| Stop | `Shift+F5` | end debugging |

## In a script

Same breakpoints, then **Run → Start Debugging** (`F5`) → *Python File*. Or put `breakpoint()` on a line in your code — Python pauses there even from the terminal (type `n` for next line, `p variable` to print, `c` to continue, `q` to quit).

## A useful habit: trace tables by hand, then check with the debugger

Before running a loop, predict the variables per iteration on paper:

```python
def largest_gap(amounts):
    biggest = 0
    for i in range(1, len(amounts)):
        gap = abs(amounts[i] - amounts[i - 1])
        if gap > biggest:
            biggest = gap
    return biggest

largest_gap([10, 4, 9])
```

| iteration | `i` | `amounts[i-1]` | `amounts[i]` | `gap` | `biggest` after |
|---|---|---|---|---|---|
| 1 | 1 | 10 | 4 | 6 | 6 |
| 2 | 2 | 4 | 9 | 5 | 6 |

Then debug the cell and step through it: were you right at every row? When your trace table and the debugger disagree, you've found exactly where your mental model is wrong. That's the most valuable moment in learning to program.

## Conditional breakpoints

Right-click a breakpoint → **Edit Breakpoint** → *Expression*, e.g. `i == 500`. The debugger stops only when it's true — essential for loops over big data.
